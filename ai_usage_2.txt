**У твоєму дизайн-документі (`duck_lang.pdf`) уже є власні конструкції, яких у репозиторії немає:**

**Мінімальний набір змін:**

```
statement  ::= var_decl | ident_stmt | print | if | while
ident_stmt ::= ident ( "<-" expr | "🔀" ident ) ";"
print      ::= "🔊" expr ";"
while      ::= "🔁" expr block
```

- Присвоєння і swap обидва починаються з `ident`, тому в EBNF їх треба обʼєднати в один лівофакторизований `ident_stmt`. У парсері достатньо після `ident` подивитись на наступний токен.
- Нові вузли: `SwapNode(left, right)` і `PrintNode(expr)`, у дампі, наприклад, `Swap a b` і `Print` з вкладеним виразом.
- Нові послідовності для таблиці й лексера:

- `🔀` = `0xF0 0x9F 0x94 0x80`
- `🔁` = `0xF0 0x9F 0x94 0x81`
- `🔊` = `0xF0 0x9F 0x94 0x8A`
- Якщо замінюєш `waddle` на `🔁`, це зачепить 4 тести з `waddle`. Їх треба оновити або залишити `waddle` як синонім.

**Якщо хочеш ще трохи (на вибір, не обовʼязково):**

- Ланцюговий swap-ротація: `ident "🔀" ident { "🔀" ident } ";"`. Це лише цикл у парсері, але в stage 2 доведеться визначити семантику.

## Рішення 1: верхній рівень і «вийти з функції зі значенням»

**Верхній рівень.** Варіанти:

- спершу оголошення, потім оператори;
- усе вперемішку: `program ::= { top_item } finish`.

Раджу друге: кожне оголошення починається з власного ключового слова, парсер просто дивиться на перший токен. Вкладених функцій не робимо, оголошення лише на верхньому рівні.

**Повернення значення.** Варіанти:

- перевикористати `finish`;
- окреме слово, наприклад `lay` (качка «знесла яйце») + емодзі на твій вибір.

Раджу окреме слово. Твій `finish` уже має спеціальні правила: він останній у програмі, і є помилки «missing finish» та «must be the last». У функції правила інші (кілька повернень, повернення з вкладених блоків), тож змішування сплутає і парсер, і семантику. Парсер дозволяє `lay` у будь-якому блоці, а «`lay` поза функцією» ловить семантичний прохід.

## Рішення 2: функції й виклики

Синтаксис у стилі твоїх оголошень: `swim name(a: 🐥, b: 🦆): 🐥 🪶 … 🪽`. Тип результату через `:`, як і в `var_decl`. Тип результату обовʼязковий, як вимагає завдання, тому `void` не потрібен.

Виклик: звичайне `f(x, g(y))`. Екзотичний виклик подвоїть кількість парсерних і тестових випадків, а «свого» в тебе й так вистачає (🔀, 🔊). Це перша ж ідентифікатор-конструкція, тож після `ident` парсер дивиться на `(`.

Параметри: константні за замовчуванням. Функція бачить лише параметри й локальні змінні, а не змінні верхнього рівня. Це спрощує і семантику, і кодогенерацію.

Через результат-тип нам потрібні виклики як оператори (`p.move(1);`, значення відкидається). Без цього методи, що змінюють поля, ніде не викличеш.

## Рішення 3: структури, обʼєкти, ланцюги

**Поля.** Раджу повторити `var_decl` без ініціалізатора: `🍃 x: 🐥;` або `🪨 y: 🐥;`. Це та сама логіка «кожна сутність має мутабельність».

**Створення обʼєкта.** Варіанти:

- позиційно, як виклик: `Point(1, 2)`;
- за іменами: `Point { x: 1, y: 2 }`.

Раджу друге: парсер одразу відрізняє виклик від створення, і семантика перевіряє «значення для кожного поля» за іменами. Не використовуй для цього `🪶 … 🪽`: `🐤 flag 🪶 …` стане неоднозначним (`flag 🪶` схоже на початок литерала). Саме тому `{ }` тут безпечні, бо ти не вживаєш їх як блоки.

**Доступ до поля.** Варіанти:

- класична крапка `c.center.x`;
- емодзі-доступ, наприклад `c 🐾 center 🐾 x`.

Парсер той самий, токен інший. Якщо хочеш ще одну «свою» синтаксичну відмінність дешево, бери емодзі. Тільки одноточкові емодзі без селектора `FE0F`, інакше лексер прочитає зайві байти `EF B8 8F`.

**Ланцюги і присвоєння.** Це постфіксний цикл: `operand { "." ident [ args ] }`. Крапка з `(` означає виклик методу, без нього доступ до поля. Присвоєння в поле, `c.center.x <- 5;`, перевіряє семантика: на кожному кроці ланцюга поле має бути `🍃`, а корінь змінною `🍃`.

Заодно swap можна дозволити для будь-яких таких цілей, `p.x 🔀 p.y;`. Синтаксично це безкоштовно.

## Рішення 4: методи

Метод оголошується всередині структури, поруч із полями. `self` не потрібен, бо в тілі поля й методи видно за іменем.

**Правило «метод, що присвоює поле, викликається лише на мутабельному обʼєкті».** Варіанти:

- виводити з тіла метода: потрібна транзитивна аналітика, бо методи викликають один одного;
- явна позначка: `🍃 swim move(...)` змінює обʼєкт, `🪨 swim len(...)` ні.

Раджу явну позначку. Вона вписується в твою мову, де кожне оголошення має `🍃`/`🪨`. Семантичні правила тоді локальні:

- `🪨`метод не присвоює поля і не викликає `🍃`методів;
- `🍃`метод можна викликати лише на `🍃`обʼєкті.

Лише не забудь описати це в README як спосіб виконання вимоги.

## Рішення 5: read і print

`🔊` уже є. Додається лише рядковий літерал. Тримай його тільки в `print`, а не в `expr`, бо рядкового типу немає: `print ::= "🔊" ( string | expr ) ";"`. Лексеру потрібен рядок у лапках; байти всередині можуть бути будь-якими, тож емодзі в рядку працюють самі. Нетермінований рядок дає лексичну помилку `line:col`.

Для `read` треба вирішити, якого він типу (i32 чи i64). Раджу `👂 🐥` або `👂 🦆`: тип пишеш явно, і виводити нічого не треба. Альтернатива: завжди i64 з перевіркою при присвоєнні в i32.

## Чернетка граматики

```
program     ::= { top_item } finish
top_item    ::= func_decl | struct_decl | statement

func_decl   ::= "swim" ident params ":" type block
params      ::= "(" [ param { "," param } ] ")"
param       ::= ident ":" type

struct_decl ::= "flock" ident "🪶" member { member } "🪽"
member      ::= ( "🍃" | "🪨" ) ( ident ":" type ";"
                               | "swim" ident params ":" type block )

statement   ::= var_decl | simple_stmt | print | if | while | return
simple_stmt ::= postfix [ "<-" expr | swap_tail ] ";"
swap_tail   ::= "🔀" postfix { "🔀" postfix }
print       ::= "🔊" ( string | expr ) ";"
return      ::= "lay" expr ";"

expr        ::= arith [ ( "≡" | "≢" ) arith ]
arith       ::= term { ( "+" | "-" ) term }
term        ::= postfix { ( "*" | "/" ) postfix }
postfix     ::= operand { "." ident [ args ] }
operand     ::= ident [ args | object_lit_tail ] | number | "🪺" | "🪹"
              | "(" expr ")" | "👂" type
args        ::= "(" [ expr { "," expr } ] ")"
object_lit_tail ::= "{" ident ":" expr { "," ident ":" expr } "}"
type        ::= "🐥" | "🦆" | "🥚" | ident
```

Дві нотатки до цієї чернетки:

- У `simple_stmt` парсер спершу читає `postfix`, а потім перевіряє: зліва від `<-` або `🔀` має стояти ланцюг ідентифікаторів без викликів, а самотній `postfix` має закінчуватися викликом. Це контекстне правило, випиши його в `grammar.ebnf` коментарем, щоб граматика чесно збігалася з парсером.
- Старе `finish operand ;` краще замінити на `finish expr ;`. Перевір тести `finish_*`, бо якийсь недійсний тест може змінити очікувану помилку.

### 1. Верхній рівень та повернення значення (lay)

- Верхній рівень: Повністю підтримую рішення розділяти оголошення за власними ключовими словами (наприклад, swim для функцій, flock для структур). Парсер дивиться на перший токен рядка/інструкції і одразу розуміє, чи це функція, структура чи звичайний statement. Ніяких вкладених функцій — це суттєво спрощує і таблицю символів, і кодогенерацію.
- Повернення (lay): Використання окремого ключового слова на кшталт lay (качка знесла яйце) разом із виразом (lay expr;) є чудовим і тематичним рішенням. Оскільки finish має специфічне призначення (завершення всієї програми на верхньому рівні), змішувати його з локальним виходом із функцій не варто.

### 2. Оголошення функцій та питання про void

- Стиль оголошення: Твоя інтуїція щодо стилю на кшталт Rust (fn add(...) -> type або в нашому стилі swim name(...) -> type) абсолютно правильна. Це набагато простіше для рекурсивного спуску (recursive descent), ніж C++ стиль. Коли парсер бачить назву функції та параметри, він чітко знає, що далі йде стрілочка (або двокрапка) і тип результату, і лише потім блок коду 🪶 … 🪽. Це повністю усуває неоднозначність із розпізнаванням оголошення змінних.
- Чи потрібен void (функції без повернення)? Згідно з вимогами завдання («a declaration with typed parameters and a result type, a body, and a way to leave the function with a value»), кожна функція повинна мати тип результату та завершуватися інструкцією повернення (lay). У таких навчальних мовах зазвичай не реалізують void окремо, щоб не ускладнювати семантичний аналізатор перевірками «чи обов'язковий тут lay». Якщо тобі потрібна функція, яка нічого корисного не обчислює, можна просто повертати якесь значення за замовчуванням (наприклад, 0 типу 🐥), але сама функція за синтаксисом зобов'язана мати тип і завершуватися lay.

### 3. Структури: імена полів vs позиційні, та чому { } безпечні

- Декларація за іменами полів: Оголошення всередині структури через 🍃 x: 🐥; або 🪨 y: 🐥; є набагато зручнішим і гнучкішим, ніж позиційне, бо порядок полів при ініціалізації об'єкта може бути будь-яким, а код стає самодокументованим.
- Чому { } для ініціалізації безпечні (і чому Клод застерігав від емодзі 🪶): У твоїй мові блоки коду вже використовують емодзі дужки 🪶 … 🪽. Якщо б ти спробувала використати їх ще й для створення об'єктів (наприклад, Point 🪶 x: 1, y: 2 🪽), виникла б жорстка лексична та синтаксична амбівалентність. Парсер не зміг би відрізнити початок блоку коду від початку літерала структури після ідентифікатора. А от фігурні дужки { } у твоїй мові взагалі не задіяні під блоки, тому вони ідеально підходять для літералів: Point { x: 1, y: 2 }. Парсер одразу бачить ім'я, за ним {, і розуміє — це створення об'єкта.
- Обмеження для 🔀: Операція обміну (p.x 🔀 p.y) синтаксично дозволена лише для лівих значень (lvalues), тобто змінних та доступів до полів (postfix), але не для результатів викликів функцій. Це легко контролювати на етапі семантичного аналізу.

### 4. Мутабельність методів (🍃 / 🪨)
Клод запропонував дуже елегантне рішення, яке ідеально вписується у філософію твоєї мови (де кожна змінна/поле має маркер мутабельності 🍃 або 🪨):

- Оскільки оголошення членів структури починаються з 🍃 або 🪨, методам теж можна задати цей префікс:

- 🍃 swim move(...) — мутабельний метод (може змінювати поля об'єкта). Його можна викликати лише на мутабельному об'єкті (🍃 p).
- 🪨 swim len(...) — незмінний метод (тільки читає поля або інші 🪨-методи). Його можна викликати як на мутабельних, так і на константних об'єктах.

### 📝 Фінальна чернетка граматики (grammar.ebnf)
program     ::= { top_item } finish

top_item    ::= func_decl | struct_decl | statement

func_decl   ::= "hatch" ident params "->" type block
params      ::= "(" [ param { "," param } ] ")"
param       ::= ident ":" type

struct_decl ::= "flock" ident "🪶" member { member } "🪽"
member      ::= ( "🍃" | "🪨" ) ( ident ":" type ";"
                               | ( "🍃" | "🪨" ) "hatch" ident params "->" type block )

statement   ::= var_decl | simple_stmt | print | if | while | return
simple_stmt ::= postfix [ "<-" expr | swap_tail ] ";"
swap_tail   ::= "🔀" postfix { "🔀" postfix }
print       ::= "🔊" ( string | expr ) ";"
return      ::= "lay" expr ";"

expr        ::= arith [ ( "≡" | "≢" ) arith ]
arith       ::= term { ( "+" | "-" ) term }
term        ::= postfix { ( "*" | "/" ) postfix }
postfix     ::= operand { "." ident [ args ] }
operand     ::= ident [ args | object_lit_tail ] | number | "🪺" | "🪹"
              | "(" expr ")" | "👂" type
args        ::= "(" [ expr { "," expr } ] ")"
object_lit_tail ::= "{" ident ":" expr { "," ident ":" expr "}"
type        ::= "🐥" | "🦆" | "🥚" | ident

2. Видимість у функціях/методах: Всередині методів структури імена шукаються спочатку серед параметрів і локальних змінних, потім серед полів структури, і в кінці — серед глобальних змінних.
3. Мутабельність методів:

- Методи з префіксом 🍃 (наприклад, 🍃 hatch ...) можуть змінювати поля структури і викликаються лише на мутабельних об'єктах (🍃 obj).
- Методи з префіксом 🪨 (🪨 hatch ...) є константними (тільки читають поля) і можуть викликатися як на мутабельних, так і на константних об'єктах.

1. Обмін значень (🔀): Використовується виключно для змінних та полів (postfix зліва та справа), але не для результатів викликів функцій.

### 1. Боротьба з пріоритетом операцій (Operator Precedence)
У програмуванні існує чіткий порядок виконання операцій: множення/ділення виконується раніше за додавання/віднімання, а доступ до полів (.), виклики функцій ((...)) та індексація мають найвищий пріоритет серед усіх можливих операцій.

Якщо подивитися на вираз на кшталт: a.b.c * 2 + 1

Парсер повинен спочатку «згорнути» ланцюжок доступу до полів (a.b.c), потім помножити його на 2, і лише в кінці додати 1. Якщо не виділити postfix на окремому рівні ієрархії граматики, парсер заплутається в тому, що саме до чого застосовується, і порядок обчислення поламається.

### 2. Захист від плутанини в логіці завдань (наприклад, з 🔀 або присвоєнням <-)

Рівень postfix у граматиці ідеально вирішує цю проблему:

- Базовий operand — це просто ідентифікатор, число, літерал або дужки.
- Постфіксна частина (postfix) дозволяє додати до цього операнда нуль або більше постфіксів: крапки з полями (.ident), виклики ((...)) тощо. Коли парсер чи семантичний аналізатор перевіряє ліву частину для <- чи 🔀, він каже: «Мені потрібен саме postfix (ланцюжок змінна/поля), який не закінчується викликом функції». Це робить перевірки в семантичному пассі надзвичайно простими та чистими.

### 3. Чистота структури AST (Abstract Syntax Tree)
Коли парсер розбирає конструкцію через postfix, він природним чином будує дерево для вкладених викликів та доступів. Наприклад, вираз p.move(5) парситься як:

- Операнд: p
- Постфікс: виклик методу move з аргументом 5 на базі p.
Це допомагає уникнути «спагеті-коду» в парсері, де тобі довелося б вручну писати складні циклічні перевірки на кожному кроці. А завдяки тому, що правила в EBNF пишуться чітко одне за одним (postfix ::= operand { "." ident [ args ] }), кожна функція твого рекурсивного спуску відповідає чітко за свій рівень абстракції!

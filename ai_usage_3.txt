Final design: `raft<type, size>` has a length evaluated once at creation and fixed afterward. It can
be initialized with values or with default zero/false values; indexing supports reads and writes,
known out-of-range indices are rejected during compilation, and dynamic indices are checked at
runtime. Passing a raft to a function makes a copy. The unrelated IR checklist for other features was
not part of the arrays implementation.

Answer summary: There is nothing wrong with the `raft<duck32, n>` syntax itself. The initial
compile-time-only design would not support the user's intended semantics, so the size expression
must instead be evaluated once when the raft is created, validated, and stored with the data. A later
change to the source variable does not resize that raft.

User's follow-up design choices:

The user clarified that a size expression may be a number, an expression, or a variable assigned or
changed earlier in the program, and suggested a positive-size check and upper bound to limit memory.
The chosen behavior is a 1 MiB maximum per raft, with dynamic invalid sizes reported at run time and
statically known invalid sizes rejected at compile time. Function parameters use `raft<element_type>`
and accept any length; global and local raft variables are supported.

Additional implementation work: replaced the compile-time LLVM array type with a descriptor holding
the chosen run-time length and a pointer to element storage. The length expression is evaluated once
at declaration, then checked for positivity and the per-element-type limit; later changes to its
source variable do not resize an existing raft. Dynamic index checks compare against the stored
length. Local storage uses dynamic LLVM stack allocation with stack-save/restore at block boundaries,
so repeated block execution releases its raft storage. Globals hold descriptors initialized during
main. Function arguments and whole-raft copies allocate and copy element data, preserving value
semantics; size mismatches are diagnosed at compile time when both lengths are known, or reported
at run time otherwise. Added coverage for changed size variables, expressions, globals, any-length
parameters, deep copies, zero fill, memory limits, runtime failures, and loop scopes. Updated the
README and grammar for dynamic fixed-after-creation lengths.

Prompt sent:
"окей тепер додай функціонал оптимізатора, можливо випиши його в окремий файл якщо так буде логічно:
Three transformations of the checked tree behind --optimize, run before code generation:
• Unused variables (1 point) — a declaration nobody reads is removed with its assignments, again and again until
a pass removes nothing; scopes and shadowing are respected; an expression that calls a function or read() is
never dropped.
• Unused functions (1 point) — a function nobody calls is removed with its whole body, again and again:
removing a body may leave another function unused.
• Inlining (2 points) — a function called exactly once is replaced at its call site by its body: each parameter becomes
a local declaration initialised with the argument, the exit of the body becomes the value that stands where
the call stood, names are renamed so they cannot collide with the caller’s, and the function is then removed as
unused. A recursive function is never inlined. The README says which shapes you inline and which you leave
alone, for example a body that leaves through exit inside an if.
The proof is mechanical. A folder of at least 6 programs, two per transformation, each with the expected tree after
--optimize --ast and the expected output; the output is the same with and without the flag. Every other test
of your suite also passes with the flag. Add to the README one before/after excerpt of the IR for the inlining of
one function"
